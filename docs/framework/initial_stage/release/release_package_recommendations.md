Не “сервер с текстовыми ответами”, а именно структурированная подача знаний и процедур. MCP для этого хорошо подходит, потому что он умеет отдавать агенту resources (данные/доки), tools (действия) и prompts (шаблоны инструкций); это не замена знаниям, а шина доставки контекста. ### 1. Жёсткий “конституционный” слой в репозитории
Сначала дай агенту не всю документацию, а короткий обязательный свод правил, который читается в начале работы.

Для Codex это AGENTS.md: он читает такие файлы до начала работы, умеет наслаивать глобальные и project-specific инструкции от корня к текущей папке, и по умолчанию режет суммарный объём на 32 KiB, так что файл должен быть плотным и без воды. Для Claude Code есть CLAUDE.md, но важно понимать: он подаётся не как system prompt, а как user message, поэтому это сильная подсказка, но не магическая гарантия послушания. Cursor, в свою очередь, поддерживает project rules через .md и .mdc, причём .mdc можно навешивать по glob-ам через frontmatter. ы быть не “рассуждения о философии”, а вещи уровня:

какие сущности в фреймворке первичны;
какие инварианты нельзя нарушать;
какие паттерны запрещены;
как выглядит минимальный правильный модуль;
как запускать проверки;
какие команды агент обязан выполнить после изменения кода.

То есть не “объясни всё”, а “не дай сойти с рельс”.

2. Канонические примеры важнее длинной прозы

Если концепции нетривиальные, агенту нужны golden examples. Не один большой демо-проект, а несколько маленьких эталонов:

минимальный runtime component;
минимальный extension/plugin;
пример правильного lifecycle;
пример anti-pattern и чем он плох.

Это то, что реально переучивает модель на нужную парадигму. Проза полезна для понимания, но форму кода агент быстрее схватывает по образцам и тестам, чем по абстрактным текстам.

3. Навыки/skills для типовых операций

Для повторяемых задач вроде “создай новый runtime step”, “добавь resource adapter”, “оформи domain object по правилам фреймворка” я бы сделал отдельные skills.

У Codex skill — это пакет из инструкций, ресурсов и опциональных скриптов; он использует progressive disclosure: сначала держит в контексте только метаданные навыка и подгружает полный SKILL.md только когда решает его применить. У Claude Code похожая идея: SKILL.md добавляет навык в тулкит, и он может триггериться автоматически по релевантности. Это очень хорошая штука именно для “писать код в нашей манере”, потому что ты не грузишь в каждый запрос весь трактат о фреймворке. S/CLAUDE/rules** — для общих рамок;

skills — для конкретных рабочих сценариев;
RAG — для глубоких справок.
4. RAG нужен, но локальный и read-only

Да, локальный RAG над документацией нужен. Но не как единственный механизм, а как справочная глубина.

Лучший вариант здесь — локальный индекс + MCP-обёртка. OpenAI прямо описывает remote MCP как способ работы с инструментами и внешними источниками; для knowledge-backed MCP они рекомендуют read-only схему с двумя инструментами типа search и fetch. MCP-сервер может работать поверх вашего локального индекса, vector store или файловой базы, а наружу агенту давать уже аккуратный интерфейс поиска и получения фрагментов. вер, который сам текстом отвечает на типовые вопросы”?
Потому что это быстро превращается в второго галлюцинирующего агента перед агентом. Гораздо надёжнее, когда сервер делает одно из трёх:

ищет релевантные фрагменты;
возвращает точные выдержки/файлы;
отдаёт структурированные артефакты: примеры, схемы, шаблоны, glossary entries.

Пусть синтез делает основной агент, а не ваш knowledge-сервер.

5. Интернет-доступный RAG/MCP — только как вторичный контур

Если проект open source и ты хочешь, чтобы внешние агенты тоже быстро в него въезжали, тогда публичный MCP/RAG имеет смысл. Но для основной разработки я бы не делал его главным источником истины.

Причины простые:

приватность;
контроль версий;
latency;
риск, что агент получит не ту версию документации, не тот branch и не те примеры.

Для живого фреймворка лучше, когда knowledge layer жёстко привязан к текущему состоянию репо или хотя бы к версии/commit.

6. Самый важный слой — не знания, а принуждение

Чтобы агент с первой попытки писал “в парадигме фреймворка”, ему мало объяснить мир. Надо ещё сделать так, чтобы неправильный код быстро проваливался.

Я бы добавил:

framework-specific lint/check;
тесты на архитектурные инварианты;
smoke test на минимальный модуль;
один CLI-валидатор вида python -m framework.doctor check-module path/to/module.

Вот это и есть настоящий enforcement.
Пока у тебя нет автоматической проверки “это не наш стиль исполнения runtime”, любой RAG будет всего лишь вежливой просьбой.

Что в итоге выбрать

Если совсем коротко:

Не делай ставку на один механизм. Делай так:
```
repo/
  AGENTS.md                      # короткие общие правила для агента
  CLAUDE.md                      # если работаешь с Claude Code
  .cursor/rules/*.mdc            # если работаешь в Cursor
  docs/
    architecture/
    glossary/
    cookbook/
    adr/
  examples/
    golden/
    anti_patterns/
  tests/
    architecture/
    smoke/
  .agents/skills/
    create-component/SKILL.md
    add-adapter/SKILL.md
  tools/
    framework_kb_mcp/
      search
      fetch
```
И логика такая:

AGENTS/CLAUDE/rules — короткий mandatory слой;
examples — образцы формы;
skills — процедурная упаковка типовых задач;
local RAG via MCP — глубокая справка по запросу;
tests/checks — дубина, которая не даёт агенту свернуть не туда.
Что бы я не советовал

Не советовал бы:

огромный монолитный markdown на 200 страниц как единственный источник;
Q&A-сервер, который пересказывает документацию своими словами;
публичный интернет-RAG как основной источник для активной разработки;
попытку “запихнуть всю философию фреймворка в один prompt”.

Это почти всегда кончается тем, что агент помнит общие красивые слова, но код пишет старой привычной манерой.

Если хочешь, я могу дальше предложить тебе конкретную структуру AGENTS.md + схему MCP search/fetch + набор разделов документации именно под Python-фреймворк/рантайм.
